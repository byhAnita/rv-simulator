# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**嫂嫂模拟器 v11** — An LLM-Agent-driven K-pop idol dating simulator (yuri). Single-page React/Vite PWA, mobile-first (390×844px), no external CSS framework (all inline styles). Supports multiple girl groups loaded from JSON configs.

## Commands

```bash
npm run dev       # Start dev server (Vite)
npm run build     # Production build → dist/
npm run preview   # Preview production build
```

No test suite. No lint config. Validate by running `npm run build` and checking for errors.

## Architecture

### Data Flow per Round

```
Player choice → executeRound() → buildSystemPrompt() → LLM API call
→ parseLLMOutput() (4-level fallback) → validateAndFixOutput()
→ update stats/affections/memory → detect stage/event/achievement changes
→ store social feeds in pendingSocialFeeds (displayed NEXT round)
→ render story + 4 options
```

### Key Modules

| Path | Role |
|---|---|
| `src/App.jsx` | All React state, UI routing (Cover→KeyInput→Setup→Game), save/load |
| `src/agent/mainAgent.js` | Round execution, system prompt construction, JSON parsing, LLM dispatch |
| `src/agent/memoryPool.js` | Two-tier memory: M=15 summaries (100 chars each) + N=3 full stories; KKT per-member Q=10 |
| `src/agent/probabilityEngine.js` | Sub-member appearance weights: affection 40% + balance 30% + recency 20% + random 10% |
| `src/tools/llmTool.js` | Multi-model router: DeepSeek (OpenAI format), Gemini (Google format), Claude (Anthropic format), GPT-4o Mini |
| `src/rag/groupLoader.js` | Loads `public/groups/{id}/{lang}.json` → member profiles + group lore |
| `src/config/` | Game constants, 7 relationship stages, model configs, events, achievements |
| `src/i18n/` | zh/en/ko translation hook + `${var}` interpolation |
| `src/platforms/` | Social platform overlays: Bubble, Instagram, Weverse, KakaoTalk |

### State Management

- **React hooks only** — no Redux/Zustand
- **`useRef` for non-rendering data**: `statsRef`, `memoryRef`, `inputRef`, `bottomRef`
- **Module-level globals** in `mainAgent.js`: `pendingSocialFeeds`, `pendingNotifications`
- **localStorage**: API key, saves (`rv_sim_saves_v11`), language, selected model

### Adding a New Girl Group

Create `public/groups/{id}/zh.json` (+ `en.json`, `ko.json`) following the `_template/` structure. Add the group to `public/groups/index.json`. No code changes needed.

### LLM System Prompt

Built in `mainAgent.js#buildSystemPrompt()`. The prompt is ~15KB and enforces:
1. **Language first** — output language locked to player's UI language
2. **JSON schema** — strict structure; LLM must return valid JSON every round
3. **Member personality matrices** — loaded via RAG from group JSON
4. **Phase rules** — rounds 1-6 (stranger), 7-14 (familiar), 15-24 (pressure), 25+ (consequences)

JSON parsing has 4-level fallback + `validateAndFixOutput()` regex repairs for malformed responses. Temperature: 0.92, timeout: 90s.

### Social Media System

Platform content is generated by the LLM for the current round but displayed in the **next** round (delayed display reduces perceived latency). KakaoTalk unlocks per-member when affection ≥ 30.

### Relationship Stages

7 stages in `src/config/stageConfig.js`: Stranger (0–15) → ... → Trial (91–100). Stage transitions trigger special events defined in `relationshipEvents.js`.

## v12 Implemented Design

### 1. Player Identity System (Phases 1–2, implemented)

**Dual identity**: Setup page has two independent selections.

**Career identities** (`src/config/identityConfig.js`): `trainee` | `manager` | `ceo` | `artist` | `fan` | `custom`
- Background builder: `buildCareerBackground(careerIdentity, company, memberName, customText, lang)`
- Custom: LLM call at game init generates description + events stored in background
- `company` field in group JSON (`groupConfig.group.company`) used in background text

**Emotional identities**: `secret_crush` | `ex_gf` | `fate_encounter` | `none` (default) | `custom`
- `$random_` variables (meet / flipped / hiddencare / breakup / exstuff / excustom) drawn from hardcoded pools in `identityConfig.js`, picked once at init, stored in `form.identityRandoms`
- Background builder: `buildEmotionalBackground(emotionalIdentity, memberName, customText, lang, randoms)`
- **CRITICAL rule in system prompt**: emotional background is pinned EXCLUSIVELY to the named main member — sub members have no special emotional history regardless of affection level

**Player**: always a young WLW woman. Age field removed. System prompt section 3 explicitly enforces female pronouns for the player throughout.

### 2. Story Rhythm & Special Events (Phase 4, implemented)

#### 2.1 Rhythm Options

| ID | Name (zh/en/ko) | Rhythm event list | Epilogue scene |
|---|---|---|---|
| `free` | 随缘叙事 / Free Flow / 자유 서사 | None — LLM generates freely | Hometown trip with top-affection member |
| `romantic` | 浪漫情感向 | `ROMANTIC_EVENTS` | Proposal scene |
| `drama` | 修罗海王向 | `DRAMA_EVENTS` | Europe group trip |
| `pr_crisis` | 高压舆论向 | `PR_CRISIS_EVENTS` | Social media announcement |

`free` is the default (first option in Setup). It has no rhythm-specific event injections; the LLM narrates without special constraints beyond career/emotional events.

#### 2.2 Special Event Architecture (v12 queue system)

All event IDs are deduplicated (never repeat in the same save). Triggered IDs stored in `localStorage` under `rv_sim_v12_triggered_events`.

---

**Round 0 — Background-only opening scene**

LLM generates a first-meet scene: player arrives in their career context, meets ALL selected members (main + sub) and NPC members simultaneously.
- Sub/NPC members: genuine first meetings with player
- Main member: interaction colored by **emotional background** (ex-gf = reunion not first-meet; fate_encounter = morning-after awkwardness seeing her again professionally; secret_crush = she knows something the player doesn't yet)
- No special event injection, no D override, no rhythm events
- Instruction to LLM: "This is the game opening scene. Build a first-meet moment where the player arrives in their career context and encounters all group members. Base the scene on the player's career background. The player's interaction with [main member] specifically should reflect the emotional background."

---

**Intro phase (rounds 1 to `EMOTIONAL_LATE_ROUND - 1`) — Auto-injected early events**

- Round `CAREER_EARLY_ROUND = 1`: auto-inject 1 randomly selected `career.early` event
- Round `EMOTIONAL_EARLY_ROUND = 3`: auto-inject 1 randomly selected `emotional.early` event
- Both use the narrative bridge + `[SPECIAL EVENT]` block in LLM user message (same injection format as before)
- Throughout this phase, LLM is reminded that main member's behavior toward player reflects the emotional background
- No D-option queue active during intro phase

---

**Queue phase (rounds `EMOTIONAL_LATE_ROUND` onward) — Player-triggered via option D**

All remaining events enter a FIFO priority queue when conditions are met. The front item's hardcoded `intro` text replaces the LLM-generated D option. Player chooses D to trigger the event or A/B/C to defer it.

**Queue item shape:**
```js
{
  event: { id, prompt },
  memberId: "irene",        // locked at queue-entry time
  category: "career" | "emotional" | "rhythm",
  entryRound: N,
  dShownCount: 0,           // increments each round it's the active D option (not during cooldown)
  intro: { zh, en, ko }    // hardcoded player-perspective lead-in text
}
```

**D slot logic per round:**
```
1. Expire: remove items where (currentRound - entryRound) >= MAX_QUEUE_STAY
2. If queueCooldown > 0: decrement → D = custom input (dShownCount NOT incremented)
3. Else if queue non-empty:
     front.dShownCount += 1
     if front.dShownCount > MAX_D_SHOWN_COUNT → discard front, repeat from step 3
     D = front.intro[lang]
     if player chose D → pop front, inject event prompt, queueCooldown = D_COOLDOWN
4. Else → D = custom input
```

When D is taken by a queue event: tell LLM in system prompt to generate only A/B/C; D field in LLM output is ignored and overwritten with the hardcoded intro text.

**Queue entry — two-tier priority:**

| Tier | Events | Entry condition | Behavior |
|---|---|---|---|
| Priority (front) | career mid/late, emotional late | Fixed round reached | Jump to front of queue |
| Rhythm (back) | romantic / drama / pr_crisis | Affection/secrecy/gap threshold met + ID not triggered | Append to back |

Member ID locked at entry time. Same dedup: event ID checked against `triggeredEventIds` before push — if already triggered, skip.

**Queue entry rounds:**
- `CAREER_MID_ROUND = 14` → career mid enters priority queue
- `CAREER_LATE_ROUND = 28` → career late enters priority queue
- `EMOTIONAL_LATE_ROUND = 6` → emotional late enters priority queue
- Rhythm events: threshold-gated, any round from `EMOTIONAL_LATE_ROUND` onward

**Queue constants:**

| Constant | Value | Meaning |
|---|---|---|
| `MAX_QUEUE_STAY` | 8 | Rounds in queue before silent discard (never shown as D) |
| `MAX_D_SHOWN_COUNT` | 3 | Times shown as D before discard (player ignored it) |
| `D_COOLDOWN` | 2 | Rounds D reverts to custom after player triggers an event |

**Injection format (unchanged when triggered):**
```
[SPECIAL EVENT — THIS ROUND ONLY]
The story MUST open with 1–2 sentences that naturally continue or close out the previous round's situation (smooth narrative bridge). Then transition into the following required event as the main scene.
Target member: <name>
<event prompt>
```

**Rhythm event threshold rules (unchanged):**
- `ROMANTIC_EVENTS`: attraction (aff ≥ 20), ambiguous (aff ≥ 45), pre_confession (aff ≥ 70), together (aff ≥ 90)
- `PR_CRISIS_EVENTS`: low (secrecy 55–80), medium (secrecy 30–55), high (secrecy < 30)
- `DRAMA_EVENTS`: mild (gap < 10), moderate (gap ≥ 10), intense (gap > 40)
- `free` mode: no rhythm events enter queue

#### 2.3 Ending System

**Trigger condition**: `topAffection >= ENDING_MIN_AFFECTION (90)` AND `round >= ENDING_MIN_ROUND (35)`
- Checked after each round's stat update
- Uses actual top affection member across all selected members (not fixed to form.mainMember)

**HE popup**: fires once per save, full-screen overlay. Two buttons: `[End + View Epilogue]` / `[Continue Playing]`. State in `localStorage rv_sim_v12_he_shown_{rhythm}`.

**After dismissal**: persistent 5th gold button `[✨ End + View Epilogue]` appears below option row every round.

**HE descriptions** (in `specialEvents.js#HE_DESCRIPTIONS`, multilingual):
```
romantic:  zh "暧昧褪去，浪漫不死 💍"
drama:     zh "吵吵闹闹，不如一起胡闹到老 🍻"
pr_crisis: zh "舆论纷纷扰扰，你们始终十指紧扣 👭"
free:      zh "命运交错如歌，你们牵手相望 💗💛💙💚💜"
```

#### 2.4 Epilogue System

Single LLM call via `generateEpilogue()` in `mainAgent.js`. Free-form prose, no JSON schema. `handleViewEpilogue` in `App.jsx` synchronously clears options + disables normal rounds before the async call (prevents accidental normal round firing).

Epilogue uses **top affection member** (not form.mainMember) as focus for all rhythms except `drama` (which uses all selected members).

**Context injected per rhythm**:
| Rhythm | Context |
|---|---|
| `romantic` | Top member name + personality + affection + last 3 summaries |
| `pr_crisis` | Top member + all selected member names + affection values + secrecy |
| `drama` | All selected members + affection values + last 3 summaries |
| `free` | Top member name + personality + `birthplace` + affection + last 3 summaries |

#### 2.5 Custom Identity LLM Events (planned)

For `custom` career or emotional identity, fire an async LLM call immediately after round 0's story response arrives (parallel to player reading round 0).

The call generates in one JSON response:
- Career: 3 tiers (early/mid/late) × `{ prompt, intro_zh, intro_en, intro_ko }`
- Emotional: 2 tiers (early/late) × `{ prompt, intro_zh, intro_en, intro_ko }`

Stored in `form.customCareerEvents` / `form.customEmotionalEvents`. These replace the hardcoded tier lists at injection/queue-push time.

If generation is not complete when an event's fixed round is reached: defer entry to queue by 1 round. Career early (auto-inject at round 1) defers to round 2 if not ready — still well within intro phase.

### 3. Two-Tier Memory Architecture

Replace the single N-round full-story window with a two-tier system:

| Tier | Content | Length | Purpose |
|---|---|---|---|
| Tier 1 (Long) | Last M=15 round summaries | ~100 chars each | Long-term narrative continuity |
| Tier 2 (Short) | Last N=3 round full stories | Full text | Immediate context + detail |

#### Summary generation

- `summary` is a new field in the LLM JSON output schema (same single API call, no extra cost)
- LLM generates ~100-char first-person summary of the round it just wrote
- Stored per round as `{ round, memberId, summary }` — `memberId` = main member of that scene
- Never displayed to the player; only used to build next-round prompt context
- Pre-Phase 5 (before subagent split): summary comes from the existing single LLM call

#### Memory shape (`createEmptyMemory`)

```js
{
  playerStats: null,
  affections: {},
  topMemberId: null,
  summaries: [],        // [{round, memberId, summary}]  max M=15, FIFO
  fullStories: [],      // [{round, story, playerChoice}] max N=3, FIFO
  kktMessages: {},      // {memberId: [{sender, content}]} max Q=10 per member
  stageChanges: [],
  memberAppearances: {},
  npcAppearances: {},
  // socialPosts REMOVED — social content is ephemeral, displayed next round and discarded
}
```

#### Prompt injection (`buildMemoryContext`)

```
[Long Memory — up to 15 summaries]
R3(irene): Late-night practice, she fixed your collar, tension rose.
R4(wendy): Group meal, Wendy kept refilling your drink.
...

[Recent Stories — last 3 rounds]
=== Round 15 ===
<full story text>
Choice: B

=== Round 16 ===
...
```

#### KKT injection rule

- KKT history is stored per member ID in `kktMessages`, max Q=10 messages each
- At prompt build time, inject **only the KKT entries for members selected by the probability engine for this round** (i.e. members who will appear in the story)
- Members with affection < 30 still cannot unlock KKT (existing rule unchanged)

#### Save/load compatibility

- `rv_sim_saves_v11` shape changes: `storyRounds` → `summaries` + `fullStories`, `socialPosts` removed
- Old saves are **intentionally broken** by this change (same stance as Phase 2)
- Migration guard: on save load, if `memory.summaries === undefined`, reset memory to `createEmptyMemory()` and log a warning — do not crash

#### Files changed in Phase 3

| File | Change |
|---|---|
| `src/agent/memoryPool.js` | New shape, new `updateMemory` params, new `buildMemoryContext` two-tier output |
| `src/agent/mainAgent.js` | Add `summary` to JSON schema + prompt; pass `summary` to `updateMemory`; filter KKT by round members |
| `src/App.jsx` | Save/load migration guard; form normalization includes `summaries`/`fullStories` |

### 4. Dual Subagent Architecture

#### Subagent definitions

**Story Subagent** (primary, heavier):
- Context: shared context (M summaries + current stats + member profiles) + last N full stories + special event injection (if triggered this round)
- Output: `{ summary (→ memory only, not displayed), story, statDeltas, affectionDeltas, options[4] }`

**Social Subagent** (secondary, lightweight):
- Context: current round's story text + member profiles + platform style rules
- Output: `{ bubble, instagram, weverse, kkt }` — KKT injection uses only that member's Q-round history
- No memory pool needed; social content is ephemeral

#### Round Flow (v12)

```
┌──────────────────────────────────────────────────────────────────────┐
│                         v12 Round Flow                               │
├───────────────────────────────┬──────────────────────────────────────┤
│ AGENT SIDE                    │ UI SIDE (player-facing)              │
├───────────────────────────────┼──────────────────────────────────────┤
│                               │                                      │
│  [Player submits Round N]     │                                      │
│         ↓                     │                                      │
│  ┌──────────────────────┐     │                                      │
│  │ Story subagent N+1   │─────┼──► UI: show Round N social          │
│  │ fires (async)        │     │    (stored from social agent N,      │
│  └──────────────────────┘     │     released here)                   │
│  ┌──────────────────────┐     │    Player browses Round N social     │
│  │ Social subagent N+1  │     │    while story N+1 generates         │
│  │ fires simultaneously │     │                                      │
│  │ context: shared +    │     │                                      │
│  │ Round N story text   │     │                                      │
│  │ (already complete)   │     │                                      │
│  └──────────┬───────────┘     │                                      │
│             │ resolves fast   │                                      │
│             ↓                 │                                      │
│  store social N+1 output      │  (UI does NOT refresh here)          │
│             │                 │                                      │
│  Story subagent N+1           │                                      │
│  resolves ────────────────────┼──► Display Round N+1 story + options │
│                               │    Player reads, makes choice        │
│                               │                                      │
│  [Player submits Round N+1]   │                                      │
│         ↓                     │                                      │
│  Story subagent N+2 fires ────┼──► UI: show Round N+1 social        │
│  Social subagent N+2 fires    │    (stored from social agent N+1,    │
│  (simultaneously)             │     released here)                   │
│  ...                          │    Player browses while N+2 generates│
└───────────────────────────────┴──────────────────────────────────────┘

Key invariants:
- On player submit: story subagent N+1 and social subagent N+1 fire simultaneously
- Social subagent N+1 context = shared memory + Round N story text (already complete,
  available immediately) — no dependency on story N+1
- Social subagent N+1 finishes quickly; output stored; UI does NOT refresh yet
- Story subagent N+1 finishes; UI immediately displays Round N+1 story
- Round N+1 social is released to UI only when player submits Round N+1
  (i.e., at the start of Round N+2's loading wait)
- All three timelines (story agent, social agent, UI) are fully decoupled
```
